# Deviations and interpretations

Where SPEC.md (draft 3) was ambiguous or could not be followed literally, this
is what was done. Section 2 decisions are unchanged.

| # | Spec says | What was done | Why |
|---|---|---|---|
| 1 | 4.1: `PUT /notes/:id` returns 409 "with the current version" | 409 body is `{ "error": { "code": "version_conflict", "message", "version": <n> } }` | Keeps the one error format of 4.1 while carrying the version. |
| 2 | 6.3: save rejected if note is in Trash; no status given | 409 with code `in_trash`; the editor shows it as "Not saved" and does not retry | Distinct from a version conflict, not a 404 (the note exists). |
| 3 | 6.1/7.2: "updated" timestamp | Only title/body saves change `updated_at`; folder, tag and Trash changes do not | Matches `version`, which those changes also leave alone. |
| 4 | 7.1: folder view | A folder view lists the notes directly in that folder; search narrowed to a folder includes subfolders (as 7.3 says) | Simplest reading. |
| 5 | 6.2: tables "with an optional header row" | Header cells are accepted only in the first row; every row must have the same number of cells; pasted tables lose spans and column widths | Enforces "header row" and "no merged cells" on the server and on paste. |
| 6 | 5: size units | 1 MB = 1,048,576 bytes; `NOTES_USER_QUOTA_MB` is in MiB (default 1024 = 1 GiB) | One consistent binary unit. |
| 7 | 8.2: permitted methods `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call` | Those are served exactly as written (2025 protocol, stateless, JSON responses). `server/discover` is also accepted, because the current stable MCP TypeScript SDK (v2, `@modelcontextprotocol/server` 2.4) implements the 2026-07-28 protocol revision, where `server/discover` replaces `initialize` and `ping` no longer exists. Every other method gets JSON-RPC -32601; an unknown tool name gets -32602; batches get -32600. | The instructions require the current stable SDK; serving both revisions keeps 2025-era and 2026-era clients working. Tests cover both. |
| 8 | 8.2: "no SSE stream" | `responseMode: 'json'`: every POST is answered with one JSON body (or 202 for a notification). The tool capability is advertised with `listChanged: false`. | As specified. |
| 9 | 8.3: title "1-200 characters" | Title is trimmed and control characters removed, then 1-200 Unicode code points. | "Characters" read as code points. |
| 10 | 12: `.env` holds `NOTES_HOST`, `NOTES_USER_QUOTA_MB`, `NOTES_AGENT_RATE_PER_HOUR` | Those three are the only `.env` settings. The app also reads `NOTES_TRUSTED_PROXY` (set to the fixed subnet `172.30.87.0/24` in `docker-compose.yml`, not in `.env`), `NOTES_DATA_DIR` and `PORT` (set in the image) and `NOTES_WEB_DIR` (tests only). | The trusted subnet must match the Compose network, so it lives next to it. |
| 11 | 11: Caddy logs | Besides deleting `Authorization`, `Cookie`, `Proxy-Authorization` and `Set-Cookie`, the Caddyfile strips the query string from logged URIs, matching the app's own log rule. | Consistency; nothing sensitive is in query strings anyway (search uses POST). |
| 12 | 6.5: images served with "private caching" | `Cache-Control: private, no-cache` with an `ETag`: the browser may keep a copy but must revalidate it, with the session, before each use (304 for the owner, 404 for anyone else). | A year-long fresh cache let another person using the same browser see a previous user's images. |
| 13 | 7.3: search "can be narrowed to a folder ... or a tag" | `POST /api/search` also accepts `unfiled: true`, used by the Unfiled view. | Narrowing after the 50-result limit lost matches. |
| 14 | 9: `data copy` | Takes no lock that blocks the app. While it runs, a marker file in `/data/copy-locks` makes image clean-up postpone deletions (a marker older than 6 hours is ignored). It builds the copy in `<dir>.partial-<pid>` and renames it when complete, and fails, leaving nothing, if an image file is still missing after a second look. | A copy that silently lacks images is worse than no copy, and the app must keep working during it. |
| 15 | 6.3: deleting a note | The editor does not move a note to Trash while its latest changes are unconfirmed (it says so); sign-out completes only when the server confirms it. | Both paths could otherwise lose changes or leave a live session. |
| 16 | 11: requests are scoped by the signed-in user | Every authenticated `/api` request must carry `X-Notes-User: <user id>`, the user its tab signed in as; if it is missing or the session cookie belongs to someone else, the answer is 401 `wrong_user` and nothing changes. Two exceptions: `GET /api/session` (added; part of signing in, it returns only the cookie's user id and name, so a new tab can learn who it is) and `GET /api/images/<id>` (an `<img>` element cannot send a custom header; the image is still served only to its owner). A tab keeps its user id, across reloads, until a sign-in or confirmed sign-out in that tab. | Tabs share one cookie: after another tab signs in as someone else, a stale tab must not act on, or open, that account. |
| 17 | 6.5: image clean-up "runs when the app starts, once every 24 hours, and after a permanent delete or Empty Trash" | It also runs when a `data copy` ends, to carry out deletions postponed during the copy. A save that refers to a removed image gets 400 `image_missing` with the image ids, and the editor offers to remove them. | Postponed work must not wait a day; a draft older than the 24-hour rule needs a clear way out. |
| 18 | 6: the web layout is sidebar, note list, editor | Added at the owner's request: on wide screens the sidebar and the note list can each be collapsed (« in the panel, a slim strip to bring it back, with `aria-expanded`/`aria-controls`), giving the editor their width. The choice is remembered per browser in `localStorage` (`notes:layout`; failures tolerated). Narrow screens are unchanged: one panel per screen, no collapse controls. | Owner request after the build. |
| 19 | 10: "editor with a formatting toolbar" (order inside the editor not specified) | At the owner's request, everything about a note sits in a compact header above the toolbar, in two rows (about 56px on a wide screen): folder picker (or "In Trash"), title, Created/Updated dates (Updated follows confirmed saves), save status and Move to Trash; then the agent mark and the tags. A read-only note with no tags has only the first row. Below the toolbar there is only the body, which is the only part that scrolls. On narrow screens the rows may wrap. | Owner request after the build. |
| 20 | — (icons not specified) | At the owner's request, every icon in the web UI is a line icon from `lucide-react` (ISC licence; named imports only, so only the icons used are bundled), all 16px with a 1.75 stroke in `currentColor`. The table buttons show a short text next to the icon ("Row above", "Delete column", …) because no standard icon says above/below or left/right clearly. All colours in `styles.css` come from the `:root` tokens (the modal backdrop is now `--backdrop`). | Owner request after the build; one new runtime dependency for the web app. |
| 21 | 6.2: the marks are bold, italic, strike, inline code and link | At the owner's request there are two more marks, `textColor` and `highlight`, each with one attribute `color` that must be one of 8 names (text: ruby, garnet, amber, emerald, teal, sapphire, amethyst, onyx; highlight: topaz, coral, ruby, amethyst, sapphire, aqua, emerald, peridot; palette "Jewel"). A note stores the name, never a colour value; the stylesheet maps each name to a light- and a dark-theme value (`--tc-*`, `--hl-*`). They render as `<span data-text-color>` and `<mark data-highlight>` without inline styles; pasted HTML gets a mark only with that attribute and an allowed name, and the server rejects any other value. They combine with each other and with bold, italic, strike and link (coloured link text takes the text colour), but never apply inside code: inline code excludes other marks and code blocks allow none, and the server enforces both. Markdown has no colour syntax, so agents cannot set colours. Existing notes need no migration. To meet WCAG AA for every text colour and the link colour on every highlight, the highlight values differ slightly from the palette as given: light topaz `#f2d68b`, coral `#ffccbf`, ruby `#ffcbd0`, amethyst `#e4d0fe`, sapphire `#c1daff`, peridot `#c5e292` (a little lighter); dark topaz `#4b3a00`, coral `#642a1c`, ruby `#652832`, amethyst `#493062`, sapphire `#1d3c68`, aqua `#00434b`, emerald `#00442c`, peridot `#304001` (darker); hue and saturation unchanged. | Owner request after the build. |
